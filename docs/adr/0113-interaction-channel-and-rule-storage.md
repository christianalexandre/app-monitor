# ADR-0113 — The interaction channel's rule set and how the desktop keeps rules

## Context

ADR-0110 decided that the desktop sends a device its app's whole rule
set, at `HelloAck` and on every change (A.1), what a rule matches (B.1)
and answers (C.1), and that rules are kept per app id, those from MCP
pending until confirmed (F.1). It left open the messages, how the store
keeps a rule, and what happens when the set does not fit one frame.
This is inside the agreed architecture (`AGENTS.md`).

Evidence, 2026-10-25:

- `Hello.channels` and `HelloAck.channels` already negotiate channels
  (`protocol/proto/appmonitor/v1/core.proto`); the server accepted
  `core` and `network` only (`AppMonitorServer.SUPPORTED_CHANNELS`).
- The device's client reads at most `Protocol.MAX_FRAME_BYTES`, one body
  plus 256 KiB (ADR-0021); a mock body is at most
  `Protocol.MAX_BODY_BYTES` (ADR-0110 C.1). Two rules with large bodies
  do not fit one frame.
- `sessions.hello` already stores a protobuf message as a blob
  (SDD 09). SQLite reuses the largest rowid after it is deleted unless
  the table is `AUTOINCREMENT`
  ([SQLite, Autoincrement](https://www.sqlite.org/autoinc.html)).
- Wire generates a `oneof` as nullable fields whose constructor refuses
  two set at once (`MockRule.kt`, generated by this build).

## Options

### A. The messages

1. **One `MockRules` message holding every active rule, in match
   order.** Each one replaces the last; the device keeps no state across
   messages and an empty set clears every mock. A rule carries the
   desktop's id, the match fields of ADR-0110 B.1, a delay and a `oneof`
   of `MockResponse` or `MockFailure`. No name: the desktop shows it.
2. **Add, change and remove messages per rule.** Smaller on a change,
   but a lost or reordered message leaves the device out of step, and
   the session's start still needs the full set.

### B. How the store keeps a rule

1. **One `mock_rules` row per rule: app id, position, name, enabled,
   pending, source and times as columns, the `MockRule` without its id
   as a blob.** `AUTOINCREMENT`, so an id is never reused: M9.4's
   exchanges name the rule that answered them. The window lists rules
   from the blob, as it reads `Hello` from `sessions`.
2. **One column per field, headers in a child table.** Every field the
   protocol gains then needs a migration.

### C. A set larger than one frame

1. **Rules are sent in order while the envelope fits
   `MAX_FRAME_BYTES`; the first that does not fit and every one after it
   are left out.** Leaving out a rule in the middle would let a later
   rule match calls the developer meant for it.
2. **Split the set over several messages.** A device would then need to
   know when a set is complete.

## Decision

A.1, B.1, C.1. The channel is `interaction`; the desktop sends
`MockRules` only to a session that listed it and got it back in
`HelloAck`, first right after `HelloAck`, even when empty.

## Consequences

- The server accepts `interaction` and gains an outgoing queue per
  session (`DeviceSession.send`). An SDK that does not list the channel
  gets nothing new.
- Breakpoints and replay (ADR-0111) add their own messages to the same
  channel; `MockRules` stays whole-set.
- A rule set left short by C.1 is not shown in the window yet; M9.3's
  editor shows it.
